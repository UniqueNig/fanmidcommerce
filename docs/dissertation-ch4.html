A central technical contribution of the study, identified in Chapters One and Two as an under-documented problem, is the reliable propagation of authentication context to resolvers within the Next.js App Router. The solution is implemented in the GraphQL route handler. Apollo Server is mounted onto a Next.js route handler using the @as-integrations/next adapter, and a context function runs on every request. That function locates the caller's token, verifies its signature on the server, and places the decoded user, if any, into the context object that is then handed to every resolver. Listing 4.4 shows the actual implementation. 

const server = new ApolloServer({ typeDefs, resolvers });

// Pull the token from the Authorization header, falling back to a cookie.
const getTokenFromRequest = (req, role) => {
  const authHeader = req.headers.get("authorization");
  if (authHeader?.startsWith("Bearer ")) return authHeader.split(" ")[1];
  const cookieHeader = req.headers.get("cookie");
  if (cookieHeader) {
    const cookieName = role === "admin" ? "admin_token" : "user_token";
    const match = cookieHeader.match(new RegExp(`${cookieName}=([^;]+)`));
    if (match) return match[1];
  }
  return null;
};

const handler = startServerAndCreateNextHandler(server, {
  context: async (req) => {
    const token = getTokenFromRequest(req, "admin") || getTokenFromRequest(req, "user");
    if (!token) return { user: null };
    try {
      // Real, cryptographic signature verification happens HERE, on the server.
      const user = jwt.verify(token, process.env.JWT_SECRET);
      return { user };           // available to every resolver
    } catch {
      return { user: null };     // invalid/expired token => treated as anonymous
    }
  },
});

Listing 4.4: GraphQL route handler that builds the authenticated per-request context.

With the context reliably populated, each resolver that performs a privileged operation simply inspects it before acting. Listing 4.5 shows the create-product resolver refusing any request whose context does not carry an administrator identity. Because this check sits on the server, it cannot be bypassed by manipulating the browser: hiding or showing a button in the interface changes nothing, since it is the resolver, not the client, that ultimately grants or denies the action. 

createProduct: async (_parent, args, context) => {
  // Authorisation is enforced from the verified context, on the server.
  if (!context.user || !["admin", "superadmin"].includes(context.user.role)) {
    throw new Error("Unauthorized");
  }
  await connectDB();
  const product = await productModel.create(deriveVariantFields(args));
  return product.populate("category");
}

Listing 4.5: Resolver enforcing role-based authorisation from the GraphQL context.

A second layer of protection operates before a page is even served. A route gate, implemented as a Next.js proxy file at the project root, intercepts requests to the protected areas. Because this runs on the Edge runtime, which lacks the Node cryptography libraries, it does not attempt full signature verification; instead it cheaply decodes the token to read the role and expiry and uses that for a fast redirect decision, while the authoritative verification remains in the GraphQL handler shown above. Listing 4.6 shows the gate. 

export function proxy(req) {
  const { pathname } = req.nextUrl;
  if (pathname === "/admin/login") return NextResponse.next();

  if (pathname.startsWith("/admin")) {
    const token = req.cookies.get("admin_token")?.value;
    const payload = token ? decodeJwt(token) : null;
    if (!payload || isExpired(payload) ||
        !["admin", "superadmin"].includes(payload.role ?? "")) {
      return NextResponse.redirect(new URL("/admin/login", req.url));
    }
  }
  if (pathname.startsWith("/dashboard")) {
    const token = req.cookies.get("user_token")?.value;
    const payload = token ? decodeJwt(token) : null;
    if (!payload || isExpired(payload)) {
      return NextResponse.redirect(new URL("/login", req.url));
    }
  }
  return NextResponse.next();
}
export const config = { matcher: ["/admin/:path*", "/dashboard/:path*"] };

Listing 4.6: Edge route gate (proxy) protecting the admin and dashboard areas.

4.6 Authentication Module

The authentication module is responsible for establishing who a user is and for keeping customer and administrator privileges separate. It spans three concerns: securely storing credentials, issuing and checking session tokens, and protecting routes. Each is described in turn.

4.6.1 Credential storage and registration

When a customer registers, the password they choose is never stored in readable form. It is passed through the bcrypt hashing function, which produces a salted, one-way hash; only that hash is written to the database. At login, the supplied password is hashed again and compared against the stored value, so the plain password never needs to be kept. This means that even if the database were somehow exposed, the passwords themselves would remain protected. The registration resolver also seeds the new customer's first saved address, so that the address entered at sign-up is immediately available at checkout.

4.6.2 Token issuance

A successful login issues a signed JSON Web Token (JWT). The token encodes the user's identifier and role and is signed with a secret known only to the server. Notably, administrators and ordinary customers receive tokens with different lifetimes, reflecting their different risk profiles, as shown in Listing 4.7. 

export const generateToken = (user) => {
  const isAdmin = ["admin", "superadmin"].includes(user.role ?? "");
  return jwt.sign(
    { id: user._id, role: user.role },
    process.env.JWT_SECRET,
    { expiresIn: isAdmin ? "7d" : "365d" }, // shorter life for privileged accounts
  );
};

Listing 4.7: Role-aware JWT generation.

4.6.3 Route protection

Route protection is enforced on the server in two places, already shown in Listings 4.4 and 4.6: the GraphQL handler verifies the token's signature on every data request, while the Edge proxy gate redirects unauthenticated users away from the /admin and /dashboard areas before any page is rendered. A subtle but important detail is that the application keeps the administrator token and the customer token in separate cookies (admin_token and user_token). This allows a person to be signed in as an administrator in one area and as a customer in another without the two sessions interfering, which proved valuable during testing. 4.8 Storefront and Cart

The storefront is the part of the system the customer actually sees and uses, and three of its implementation details are worth examining: how the catalogue is filtered efficiently, how the cart keeps track of product variants, and how the two connect at the point of adding an item.

4.8.1 Server-side catalogue browsing

An early version of the shop page fetched every product and filtered them in the browser. This is fine for a handful of products but does not scale: as the catalogue grows, the page would download more and more data only to discard most of it. The implementation was therefore changed so that filtering, sorting, and pagination all happen in the database, and the browser receives only the single page of results it needs. This is exposed through a productsPage query whose resolver builds a MongoDB query from the supplied filter, as shown in Listing 4.8. 

productsPage: async (_p, { filter = {}, page = 1, limit = 12 }) => {
  await connectDB();
  const query = {};
  if (filter.category && filter.category !== "all") query["category.slug"] = filter.category;
  if (filter.search) query.name = { $regex: filter.search, $options: "i" }; // case-insensitive
  if (filter.minPrice != null || filter.maxPrice != null) {
    query.price = {};
    if (filter.minPrice != null) query.price.$gte = filter.minPrice;
    if (filter.maxPrice != null) query.price.$lte = filter.maxPrice;
  }
  if (filter.sizes?.length) query.sizes = { $in: filter.sizes };

  const sort = filter.sort === "price-asc" ? { price: 1 }
            : filter.sort === "price-desc" ? { price: -1 }
            : { createdAt: -1 };

  const total = await productModel.countDocuments(query);
  const items = await productModel.find(query)
    .sort(sort).skip((page - 1) * limit).limit(limit).populate("category");

  return { items, total, page, pages: Math.ceil(total / limit) };
}

Listing 4.8: Server-side filtering, sorting, and pagination in the product resolver.

4.9 Checkout and Paystack Integration

Checkout is the most security-sensitive workflow in the entire system, because it is where money changes hands, and its implementation was approached with that seriousness. Four mechanisms work together to make it trustworthy: server-authoritative pricing, verified payment, idempotent order creation, and accurate stock adjustment. Each is described below.

4.9.1 Server-authoritative pricing

A naive online store trusts the total that the browser sends. This is dangerous, because a determined user can alter values in the browser before they are submitted. FanMidCommerce therefore never trusts the client total. When the customer proceeds to pay, the server independently re-checks that every item is still in stock, re-validates any coupon, and recomputes the amount due from the prices held in the database. Only this recomputed figure is used to initialise the payment, so the amount charged always matches the store's own records rather than anything the browser claimed.

4.9.2 Payment and server-side verification

The payment itself is delegated to Paystack, a Nigerian payment gateway that supports card payments, bank transfer, and USSD, the three channels Chapter Two identified as important for local trust. After the customer pays, the application does not simply believe the browser's report of success. It confirms the outcome in two independent ways: a verification call back to Paystack when the customer returns to the site, and a webhook that Paystack calls directly, server to server. The webhook is authenticated by recomputing a cryptographic signature over the raw request body and comparing it with the signature Paystack attached, as shown in Listing 4.10; a request whose signature does not match is rejected outright. 

const raw = await req.text();                       // verify against the RAW body
const signature = req.headers.get("x-paystack-signature") || "";
const expected = crypto.createHmac("sha512", secret).update(raw).digest("hex");
if (expected !== signature) {
  return NextResponse.json({ ok: false, error: "invalid signature" }, { status: 401 });
}

Listing 4.10: HMAC-SHA512 verification of the Paystack webhook.

4.9.3 Idempotent, race-safe order creation

Because two independent confirmation paths exist, the return redirect and the webhook, there is a real risk that both could try to create the same order at the same moment, producing a duplicate. This is prevented at the database level by a uniqueness constraint on the order's payment reference. Whichever path arrives first creates the order; the second attempt fails the uniqueness check and is safely ignored. The operation is therefore idempotent: running it once or twice yields exactly one order. This is a direct, practical application of the reliability requirement stated in Chapter Three.

4.9.4 Accurate stock adjustment

Once an order is confirmed, stock must be reduced, and for products with per-size inventory the reduction has to apply to the specific size purchased as well as to the overall total. Listing 4.11 shows how this is achieved using a MongoDB positional array filter, with a final safeguard that clamps any value that might otherwise fall below zero. 

for (const item of items) {
  const qty = Math.abs(item.quantity);
  if (item.size) {
    // Decrement THIS size and the overall total together.
    await productModel.updateOne(
      { _id: item.product },
      { $inc: { "sizeStock.$[s].stock": -qty, stock: -qty } },
      { arrayFilters: [{ "s.size": item.size }] },
    );
  } else {
    await productModel.updateOne({ _id: item.product }, { $inc: { stock: -qty } });
  }
}
// Safety net: never display negative stock.
await productModel.updateMany({ stock: { $lt: 0 } }, { $set: { stock: 0 } });

Listing 4.11: Per-size stock decrement after a confirmed payment.
